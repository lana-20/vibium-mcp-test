# browser_click — false "element is obscured" on pages with sticky nav (MCP)

**vibium MCP · v26.5.31 · macOS darwin 25.5.0**

## Summary

`browser_click` fails with "receivesEvents check failed — element is obscured" on elements that are demonstrably not obscured. Both `@ref` and CSS selector forms are affected. The bug manifests on pages where the navigation header combines `position: sticky`, an explicit `z-index`, and `backdrop-filter` — all three together are required to trigger it. `browser_evaluate('element.click()')` and `browser_mouse_click` with coordinates both succeed on the same elements.

## Repro

**Product card link on listing page:**
```
browser_navigate { url: "https://automation-exercise.daisyladybug.com/products" }
browser_click { selector: "a[href*='/products/']" }
```

**Add to Cart button on detail page:**
```
browser_navigate { url: "https://automation-exercise.daisyladybug.com/products/prod_001" }
browser_scroll { direction: "down", amount: 5 }
browser_click { selector: "button[style*='d4552a']" }
```

**Error (both cases):**
```
failed to click: timeout after 0s: receivesEvents check failed — element is obscured
```

## Expected

`browser_click` succeeds — element is interactive and visible.

## Actual

`browser_click` reports the element as obscured and refuses to click. The element is not obscured.

## Evidence the element is NOT obscured

Verified in-session via `browser_evaluate`:

```js
// At the Add to Cart button's center point (438, 387):
document.elementsFromPoint(438, 387)
// → BUTTON > DIV > DIV > DIV > DIV > SECTION > MAIN > BODY > HTML
// The BUTTON itself is the topmost element at that coordinate.

// No ancestors with overflow clipping:
// checked all ancestors up to body — all overflow: visible

// Button bounding rect: top=367, nav bottom=71 — fully clear of nav

// Direct evaluate click works:
document.querySelector('button[style*="d4552a"]').click()
// → Cart count increments correctly
```

`browser_mouse_click` with the element's CSS-pixel coordinates also succeeds, confirming the element is at a hittable point and the false positive is inside `browser_click`'s own `receivesEvents` check:

```
browser_mouse_click { x: 319, y: 823 }
// → navigated to /products/prod_001 ✓
```

## Trigger isolation (hardening 2026-06-06)

**The bug is intermittent.** It does not reproduce on every page load or browser session. This was discovered late in hardening: a fresh browser session (`browser_stop` → `browser_start`) showed both repro paths passing unmodified on v26.5.31 with the original CSS intact.

The intermittency invalidates some earlier strip-test results. The z-index and backdrop-filter strip tests below were run during sessions where the bug *was* active and are valid. The rgba background and ARTICLE-flattening strip tests were run during a session where the base case was also passing — those results are **inconclusive**.

**Valid strip tests** (confirmed against active bug):

| Header CSS | Result |
|---|---|
| `sticky` + `z-index:50` + `backdrop-filter:blur(12px)` | **FAIL** (bug active) |
| `sticky` + `z-index:auto` + `backdrop-filter:blur(12px)` | PASS |
| `sticky` + `z-index:50` + no backdrop-filter | PASS |
| `relative` + `z-index:0` | PASS |

**Inconclusive strip tests** (base case was also passing — cannot attribute fix to the strip):

| Change | Result | Validity |
|---|---|---|
| Replace `rgba(15,26,42,0.88)` with `#0f1a2a` | PASS | inconclusive |
| Replace `A > ARTICLE` with `A > DIV` | PASS | inconclusive |
| Stub `useCart()` DOM output | PASS | inconclusive |

**Hypothesis:** the bug is hydration-timing dependent — it manifests when `browser_click` runs during a specific window in React's hydration sequence where the header's stacking context is evaluated differently. This would explain why `set_content` reproductions never trigger it (no hydration), why linear.app (different hydration pattern) doesn't trigger it, and why it is inconsistently reproducible across browser sessions.

## Cross-site hardening (2026-06-06)

Tested 4 additional sites to isolate the trigger:

| Site | Stack | Nav CSS | Click result |
|---|---|---|---|
| automation-exercise.daisyladybug.com | Next.js 16 / React 19 | sticky, z:50, blur(12px) | **FAIL** |
| linear.app | Next.js (App Router) | sticky, z:100, blur(20px) | PASS |
| var.parts | Non-Next.js | sticky, z:50, blur(8px) | PASS |
| daisyladybug.com | S3/static | sticky, z:50, blur(12px) | PASS |

**The trigger is narrower than the CSS properties alone.** linear.app is Next.js with *higher* z-index and *more* blur and still passes. The false positive appears specific to automation-exercise's particular combination of: React Context providers in the header (`useCart()`), `A > ARTICLE` block-in-inline nesting inside clickable cards, and the `rgba` semi-transparent header background — none individually confirmed as the differentiator.

## set_content reproducibility

Tested ≥8 `browser_set_content` variations with identical HTML/CSS structure including:
- sticky + z-index:50 + backdrop-filter:blur(12px) on header
- `A > ARTICLE > DIV` child nesting
- `overflow:hidden` on article
- semi-transparent background (`rgba(15,26,42,0.88)`)
- link positioned at cy≈660 (similar y to live site)

**None reproduced the failure.** The bug is not reproducible via bare HTML — it requires the live automation-exercise rendering environment.

## Workarounds

**Option 1 — `browser_evaluate` fire-and-forget (most reliable):**
```
browser_scroll { direction: "down", amount: 5 }
browser_evaluate { expression: "document.querySelector('button[style*=\"d4552a\"]').click()" }
```

**Option 2 — `browser_mouse_click` with coordinates:**
```
browser_evaluate { expression: "var r=document.querySelector(\"a[href*='/products/']\").getBoundingClientRect(); Math.round(r.left+r.width/2)+','+Math.round(r.top+r.height/2)" }
// → get coordinates, then:
browser_mouse_click { x: 319, y: 823 }
```

**Option 3 — direct URL navigation (for product card links only):**
```
browser_navigate { url: "https://automation-exercise.daisyladybug.com/products/prod_001" }
```

## Page context

- **Site:** https://automation-exercise.daisyladybug.com
- **Stack:** Next.js 16.2.7 / React 19 / TypeScript
- **Viewport:** 1200×1182, devicePixelRatio: 2
- **Nav CSS:** `position:sticky; top:0; z-index:50; backdrop-filter:blur(12px); background:rgba(15,26,42,0.88)` (~71px tall)
- **Affected elements:** product card `<a>` links on `/products`; Add to Cart `<button>` on `/products/[id]`
- **Unaffected:** CLI `vibium click` on the same elements succeeds

## Not a duplicate

MB1–MB9 all PASS on v26.5.31. This is a new, unreported issue.

**Distinct from issue #173** (var.parts `element is obscured` after add-to-cart, closed). That was a *real* obstruction — a shadcn toast (`position:fixed; z-100`) genuinely covered the button after each cart action. The bug there was `ep.Timeout = 0` causing `WaitForActionable` to give up instantly. Fixed in `d09e5eb` (v26.5.31): zero/unset timeout now defaults to 30s in `resolveWithActionability`.

MB10 is a false positive: the element is never actually obscured, so the 30s auto-wait doesn't help — the `receivesEvents` check returns immediately with the wrong answer. The `timeout after 0s` in the MB10 error message reflects an instant synchronous failure, not a wait that expired.

## Site-side fix attempt (not deployed)

Removing `backdropFilter: 'blur(12px)'` from the automation-exercise header and making the background fully opaque (`#0f1a2a`) confirmed the fix on localhost: `browser_click { selector: "a[href*='/products/']" }` succeeded immediately after the change.

**Decision: change reverted, bug kept intentionally.** automation-exercise.daisyladybug.com is the only confirmed repro site for MB10. Deploying the fix would eliminate the only reproducible test case before the vibium bug is patched. The `backdropFilter` has been restored; the site remains in its bug-triggering state until vibium fixes the false positive.

The fix is trivial when needed: replace `backdropFilter: 'blur(12px)'` with nothing and set `background: '#0f1a2a'` in `app/components/Header.tsx`.
